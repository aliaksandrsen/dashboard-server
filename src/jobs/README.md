# Модуль задач и фоновой синхронизации (JobsModule)

Данный модуль отвечает за выполнение периодических фоновых задач (Cron Jobs) и сверку данных (Reconciliation) между внешними платёжными шлюзами (Stripe) и локальной базой данных PostgreSQL.

---

## 1. Бизнес-контекст: Зачем это нужно?

В реальном бизнесе продажи и платежи происходят не только через веб-интерфейс (UI) нашего приложения, но и **в обход него**:

1. **Прямые B2B-сделки менеджеров по продажам:**
   Менеджер договорился с корпоративным клиентом об индивидуальных условиях, зашёл напрямую в панель управления Stripe (`dashboard.stripe.com`), вручную создал инвойс на $2000 и отправил клиенту прямую платёжную ссылку. Клиент оплатил заказ на странице Stripe.  
   *Без синхронизации:* в нашей базе заказов и на графиках выручки дашборда этот платёж **не появится**.
2. **Рекуррентные списания по подпискам (Subscriptions):**
   Пользователь однажды подписался на ежемесячный план. Каждые 30 дней Stripe автоматически списывает деньги с карты клиента, когда пользователь даже не заходит в наш UI. Stripe сам генерирует инвойс, который нужно подтянуть в нашу базу как совершённый заказ.
3. **«Ночной ревизор» (Страховка от сбоев вебхуков):**
   В момент оплаты клиентом на сайте наш сервер мог перезагружаться при деплое или временно потерять связь с сетью. Деньги списались, а вебхук об оплате не дошёл. Ночная сверка гарантирует, что ни один оплаченный заказ не потеряется.

> **Главный принцип:**  
> * **Stripe** — первоисточник правды по реальным деньгам (Payment Source of Truth).  
> * **База данных PostgreSQL** — источник правды для нашего UI, склада и аналитики (Application Data).  
> * **Крон-задача `data-sync.cron`** — мост, который гарантирует, что все платежи из Stripe попадают в нашу БД.

## 2. Как работает логика синхронизации

Задача `sync_stripe_orders` запускается по расписанию каждую ночь в **00:05** (`5 00 * * *`), когда нагрузка на систему минимальна:

1. **Выборка за последние 24 часа:**  
   Сервис запрашивает у Stripe API инвойсы, созданные со вчерашнего дня (`created.gte`).
2. **Проверка на дубликаты (Идемпотентность):**  
   Для каждого инвойса проверяется наличие поля `stripeInvoiceId` в таблице `Order`:
   * Если заказа с таким ID ещё нет — создаётся новый `Order` в базе Postgres. Сумма пересчитывается из центов Stripe в валюту заказа (`invoice.total / 100`), и при совпадении `customer_email` заказ привязывается к пользователю.
   * Если заказ уже существует — он безопасно пропускается (`skipped`), предотвращая задвоение выручки.
3. **Безопасная обработка ошибок:**  
   Сбой в обработке одного инвойса не прерывает обработку всей пачки, а подробно логируется.

## 3. Ручной запуск и тестирование (Триггер)

Чтобы не ждать полуночи для проверки работы или необходимости принудительной синхронизации, в модуль добавлен HTTP-эндпоинт:

* **Метод:** `POST`
* **URL:** `/v1/jobs/sync-stripe`
* **Пример ответа:**
  ```json
  {
    "message": "Stripe orders synchronization triggered successfully",
    "result": {
      "processed": 2,
      "created": 0,
      "skipped": 2
    }
  }
  ```

### Запуск через Bruno:
В коллекции `Dashboard Server API` доступен готовый запрос:
📁 **Jobs** ➔ **Trigger Stripe Sync**
